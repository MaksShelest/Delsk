## 4. A1.2 — каталог, полученный из B1

Будущий файл: **`config/vnext/catalog.b1.json`**. В этой документационной задаче он ещё не создаётся: его должен получить Codex при реализации A1.

Источник — единственный существующий `docs/vnext/data/BALANCE_VNEXT.json`. Каталог содержит ровно подмножество `items`, `recipes`, `industries`; остальные разделы B1 остаются в исходном проекте до A2. Не пытаться передать весь проектный JSON в `EconomyProfile.Read`: у него другой контракт.

| Раздел | Содержание |
| --- | --- |
| Заголовок | Версия формата, ID каталога, статус `catalog_only`, SHA-256 точных UTF-8 байтов исходного B1 |
| `items` | 34 записи: стабильный ID, название, объём единицы, справочная цена в minor, XP за единицу, источник resource/import/production |
| `recipes` | 23 базовых V1-рецепта: ID, отрасль, ступень открытия, входные количества, выход/количество, работа при полном штате, стоимость услуги на рабочий тик |
| `industries` | 6 типов переработки: ID, имя, денежная цена первого предприятия, материалы начальной стройки |

Дорожная машина не седьмая стационарная отрасль. Пять автомобилей, склады, дорожные проекты, цехи/их оснащение и глобальные параметры A1 в новый файл не копирует: это намеренная граница подмножества, а не молчаливое игнорирование полей загрузчиком.

Извлечение воспроизводимое: исходник, фиксированное соответствие полей, одинаковый порядок и результат при повторе. Можно сделать небольшой C#-помощник либо инструмент генерации данных; Python допустим только для механического извлечения JSON, не для правил валидатора и экономики. Предпочтительно не добавлять обязательную новую среду пользователю.

Обязательно независимое сравнение загруженного каталога с выбранными секциями B1: все ID, количества, цены, объёмы, XP и рецепты совпадают. Числа не перепечатывать вручную в C# и не пересчитывать по новой формуле. Изменение B1 должно выявлять устаревший catalog-файл/его provenance в проверке, а не оставлять две независимые правды.

34/23/6 — ожидание поставляемого B1 и тестов данных. Общий reader не должен запрещать любой маленький валидный fixture из-за иного числа записей.

## 5. A1.3 — строгая C#-загрузка и структурная валидация

Нужны небольшие конкретные классы/records без зависимостей от Godot, HTTP, мира или контроллеров. Можно переиспользовать существующие определения там, где смысл совпадает, не менять их ради будущего игрового XP. XP здесь — каталожные метаданные, не счётчик опыта участника.

Проверять:

1. Формат JSON, root-object, поддерживаемую версию и статус, наличие обязательных секций, ограничения размера/вложенности. B1: максимум 1 MiB входного UTF-8 JSON, явный отказ при превышении до чтения огромного файла в память.
2. Duplicate JSON keys на любой глубине, неизвестные поля внутри нового контракта, null и неверные типы. Не ослаблять `SimulationJson.Options`/старый `EconomyProfile` глобально ради нового файла.
3. Непустые стабильные ID, уникальность в своей категории, сравнение Ordinal. Одинаковая строка в разных пространствах ID сама по себе не ошибка. Допустимый шаблон ID: `[a-z][a-z0-9_-]{0,63}`; имена непустые, не более 160 символов.
4. Количества, объёмы, цены, работа и XP — целые в допустимом диапазоне. Объём/цена/количества/длительность положительные; XP и сервисные расходы неотрицательные; ступень 1–5. Не округлять дробь до целого, не использовать float в проверке денег.
5. Каждая отрасль рецепта существует; все входные/выходные ItemId и стройматериалы существуют. Входы рецепта непустые, 1–8 различных товаров, количества положительные.
6. Переполнения при `quantity × unitVolume`, `quantity × referencePriceMinor`, сумме партии и строительного набора. Использовать checked/широкие промежуточные целые и проверку диапазона, а не тихое оборачивание long.
7. Синтаксическую корректность source SHA-256. Самостоятельный reader не утверждает сверку с исходником, который не прочитал. Фактическое совпадение B1/catalog проверяет генерация/тест согласованности.

Граф доступности, экономическая окупаемость, пороги развития, влияние улучшений, вместимость каждой ступени и отсутствие технологического самозамыкания — **A2**. Успех A1 называется «структура каталога корректна», не «экономика сбалансирована» и не «профиль готов к партии».

Выход: read-only каталог и диагностика с кодом, JSON-путём/ID, понятным сообщением. Отсутствующее поле не заменять скрытым default, опечатку не исправлять автоматически. Порядок диагностик воспроизводимый. Сохранение каталога в JSON и повторное чтение сохраняют значения; это round-trip данных, не миграция игрового save.

## 6. A1.4 — отдельная проверка через существующий runner

Добавить узкий CLI-вход, например:

```text
dotnet run --project src/Research.Runner/Research.Runner.csproj --no-build -c Release -- --validate-vnext-catalog config/vnext/catalog.b1.json --output artifacts/vnext-a1
```

Проверить текущую сборку и фактический путь DLL/аргументов, прежде чем включать команду в отчёт. Новые флаги в примере ещё не существуют до реализации A1.

Для этой команды допустимы только каталог и output. Смешение с запуском мира (`--scenario`, `--economy`, `--load`, `--replay`, `--ticks`, `--controllers`, model/research и прочими simulation flags), duplicate/missing/unknown arguments — явный отказ. Не заставлять указывать сценарий для каталога.

Маршрут должен завершаться **до создания SimulationEngine, GameSession, ModelServices/runtime и controller configuration**. Не выполнять Step, не открывать Godot/браузер/HTTP, не запускать исследование. Это отдельная read-only проверка внутри существующего runner, не новый executable.

Результат в `catalog-validation.json`: статус, область `structure`, версия/ID, SHA-256 точных байтов проверенного файла, counts, диагностика. На корректном файле exit 0; на ошибке входа/контракта/структуры ненулевой exit. Выбрать и документировать конкретный код, например 2. Не завершаться 0 с полем error внутри отчёта.

Не перезаписывать непустую чужую папку результатов или файлы существующей серии. Можно разрешить пустой выделенный output, иначе понятный отказ. Если output недоступен, stderr + ненулевой exit, не ложный «отчёт сохранён». Логи/артефакты в artifacts не коммитить; допустим один маленький образец отчёта в docs/verification с указанием его происхождения.

## 7. A1.5 — проверки и критерии готовности

| Проверка | Независимое ожидание |
| --- | --- |
| Поставляемый B1 subset | 34 товара, 23 рецепта, 6 отраслей, точное совпадение выбранных секций и source SHA |
| Малый корректный fixture | Reader работает с меньшим каталогом, не хардкодит 34/23/6 |
| Duplicate/unknown/null/missing/type/version | Строгий отказ с определённым местом/кодом, исходный файл не изменён |
| Duplicate IDs/битая ссылка/пустой вход | Отказ до любого создания мира |
| Отрицательное/дробное/нулевой объём/переполнение | Отказ без округления и wraparound |
| Данные round-trip и digest | Значения сохранены; digest соответствует реально прочитанным байтам, изменение цены меняет digest |
| CLI success/failure/опасное смешение флагов | Правильные exit codes/JSON, без файлов мира/модели/новой серии |
| Повтор извлечения | Одинаковые входы дают одинаковый каталог; stale source hash обнаруживается |
| Прежний профиль и сохранение | config/economy.json и старые версии не меняются; текущие EconomyProfileTests/save-load/replay проходят |

Тесты в существующем xUnit-проекте, конкретные сценарии по риску, без зеркалирования той же формулы через тот же production helper. CLI проверить настоящим запуском собранного runner: хотя бы корректный файл, ошибочная ссылка и несовместимые аргументы. Не выдавать unit вызов метода за проверку exit code процесса.

Restore/build/test с текущими SDK/TFM из репозитория и lock-файлами. Ориентиры: restore/build timeout 180s, тестовый набор 120s, каждый короткий CLI 30s; отдельные stdout/stderr и exit code. Использовать `Delsk.sln` и существующую команду xUnit v3/Microsoft.Testing.Platform; не сочинять несовместимые флаги VSTest. Полный bounded headless gate только если изменён общий parsing/execution путь; если изменение изолировано, существующие профильные/CLI/save regression достаточны с объяснением. Godot/Android/GPU/реальная LLM для каталога не требуются и не объявляются проверенными.

Готовность A1: reader/validator/CLI действительно работают, документы и тесты воспроизводимы, старый профиль/сценарии/сохранения не изменились. После этого остановиться, открыть PR, A2 автоматически не выполнять.
