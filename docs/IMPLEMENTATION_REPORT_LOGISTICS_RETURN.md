## Результат

Валидатор сохранений больше не запрещает поздний уже загруженный груз общей проверкой ArrivalTick≤DeadlineTick. Перед новой отправкой этот запрет остаётся. Для загруженного рейса после expiry сохраняются путь, товар, возвратное место и зарплата; ReturningCargo требует просрочки и достоверного события отказа, ReturningEmpty — своевременной приёмки. Нарушения геометрии, груза, резервов, ставки и истории по-прежнему отклоняются.

Исправлена граница фаз: SetWage в phase1 перед prepare phase4 одного тика больше не активирует новую ставку посреди начатого рейса. После успешного prepare её применение переносится за EndTick. Неуспешная подготовка не меняет момент зарплаты. Численность может изменяться в пути; оплачивается фактическая группа по фиксированной ставке из прежнего верхнего резерва.

## Контролируемая проверка просрочки

В текущей статической карте обычный scheduler отсекает поздний ETA, поэтому для проверки аварийного возврата нужен намеренный неблагоприятный снимок. Только тестовая сборка ответвляет нормально загруженный рейс на тике68, меняет TTL180→18 и срок договора на created+18. Товар, место, путь, бюджет и численность не подменяются. Весь последующий путь исполняет обычное C#-ядро. Это synthetic checkpoint fork, **не игровая возможность менять срок и не replay от начала**. Тестовая reflection вызывает существующее восстановление лишь для сборки фикстуры; затем снимок проходит production invariant/config/state hash checks, а сохранение и загрузка — checksum envelope. Production API обхода проверок не добавлен.

Расчётные ожидания до запуска: expiry70 освобождает деньги и место покупателя, но груз продолжает путь. Прибытие71 отклоняется, машина физически возвращается на источник74.
