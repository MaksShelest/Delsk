Реализация — небольшими ветками и PR от согласованного состояния. Не сливать чужую незавершённую работу, не использовать force/reset/clean для упрощения старта. Перед каждой задачей прочитать AGENTS и проверить actual diff/status; статус задачи менять по факту результата, не по наличию плана.

Приоритет первого результата: проверяемый цикл без графики. Первый цикл может начинаться с подготовленного предприятия/числовой группы в сценарии и управляться scripted командами. Это fixture, а не выдача бесплатного бизнеса в обычной партии. Обязательства/выпуск/перемещение при этом настоящие, без телепортации и обхода валидатора.

Ориентир недели сохраняет §15, но это **целевой объём, не обещание календарного срока**. При нехватке времени уменьшать число ассетов, экранов и параметров; не вычёркивать население, технику, политику или автоматику. Не закрытая к месяцу система остаётся явно незавершённой задачей.

## 4. Облачное окружение и проверки

### Организация

- Небольшая ветка на задачу, сначала inspect, затем минимальная реализация+проверка; для ядра не нужен Godot на каждом PR.
- Linux runner CI — restore/build/xUnit/scenario. Windows smoke добавляется для платформенных различий. Godot import/export — отдельная bounded job, не прятать Android failure за успешным core job.
- Контент/конфигурация проверяются до запуска: ID ссылок, цены/объёмы/сроки, доступные пути, размеры footprint, переполнение и формулы. Плохой конфиг даёт понятную ошибку, а не NaN/отрицательный запас.
- Не хранить build caches, секреты, signing keys, модельные веса и длинные журналы серий в git. Хранить короткие воспроизводимые fixture и manifest примера; реальные большие результаты — artifacts CI/отдельное хранилище.
- Версии после P00 фиксируются `global.json`, package lock/central package versions, точным Godot/templates. В CI нет плавающего `latest` после выбора.

### Ограничение процессов

Каждая внешняя команда получает жёсткий timeout, отдельные stdout/stderr, командную строку без секретов, время старта/финиша и exit code. Длинный процесс запускается как фоновая управляемая сессия: проверять выход короткими ожиданиями, не блокировать рабочую сессию одним бесконечным вызовом. При timeout завершить всю принадлежащую задаче process group и убедиться в отсутствии дочерних процессов. Не убивать процессы других задач.

Начальные **лимиты**, а не измеренные длительности:

| Проверка | Timeout | Что считать успехом |
| --- | --- | --- |
| Проверка версии инструмента | 15s | Ненулевой текст версии и exit0 |
| Restore | 180s | Зависимости получены, lock сохранён; сетевой сбой отделён от ошибки проекта |
| Build | 180s | Exit0 без пропущенного compile |
| xUnit | 120s на набор; отдельный сценарий ограничен ticks | Реально выполненные тесты, число passed/failed/skipped |
| Godot import | 120s | Завершён import, нет зависшего подпроцесса |
| Headless scene smoke | 30s / явный quit-after | Сцена действительно загрузила core и вышла |
| Android/Gradle export | 600s в управляемой сессии | APK создан, пакет/подпись проверены; это ещё не device pass |
| Research pilot | 300s на прогон + maxTicks | Итог/manifest либо явный failed/timeout |

Пример для короткого core build после появления solution: `timeout --kill-after=5s 180s dotnet build Delsk.sln --no-restore > artifacts/build.stdout.log 2> artifacts/build.stderr.log`. Конкретное имя solution подтвердить по файлам (если выбран `.slnx`, обновить команду). На Windows использовать PowerShell Start-Process/WaitForExit с конечным таймаутом и завершением process tree. Таймауты длительных jobs не означают необходимость молчать до их конца: отдавать короткие обновления о результате и блокерах.

### Нужные тесты, без избыточного покрытия

1. Unit: деньги/резервы/вместимость, полное/частичное/нулевое исполнение, формула найма/ограничение мест, strict majority, права доступа.
2. Integration: S1–S7 как фиксированные сценарии; save на пути/в WIP/торгах/перед выборами и повтор событий.
3. Детерминированные сгенерированные последовательности команд на небольшой карте: после каждого тика I01–I17. Несколько seeds и перестановок подачи достаточно для конкретного риска; новый property-testing framework не обязателен.
4. Boundary: t−1/t/t+1 для окна/выдачи/поставки/брони/голосования; первый и последний рабочие интервалы для зарплаты.
5. Controller: полный прогон без LLM и fake responses (late/malformed/foreign actor/stale/duplicate), приватные DTO/ошибки.
6. Platform: один сериализованный scenario/input tape в runner и Godot на Windows/Android даёт те же хеши контрольных тиков. Если хеш отличается — не объявлять cross-platform replay выполненным.

Не писать тест, который просто повторяет код формулы без независимых числовых ожиданий. Для случайных равенств проверять правильность сохранённой перестановки и отсутствие фиксированного преимущества; не делать flaky assertion, требующий строго равных побед за маленькое число seeds.

## 5. Исследовательский протокол первого сравнения

Сначала сильный алгоритмический baseline P21. Затем три режима при одинаковом мире/семенах/информации: baseline, hybrid, hybrid+структурированные переговоры. Изменяем один исследуемый фактор; отдельно фиксируем приоритеты победы, коэффициенты, бюджет запросов и timing-policy.

Дилеммы: купить сырьё или добыть с учётом срока; поднять зарплату или выдержать паузу; продать/купить поддержку с риском победы соперника. Включить ситуации, где алгоритм хорош и модель не нужна. Свободный текст не исполняет контракт.

Начальные10 paired seeds — пилот. Показывать таблицу по каждому seed, парные разницы, медиану и разброс; оценивать требуемую выборку после пилота. Победа — одна из метрик; на ограниченном горизонте важны выпуск, контрактное исполнение, простой, безработица, предложения/кооперация, invalid/stale/fallback и затраты модели. Не исключать неудачные прогоны без заранее записанной причины.

Exact replay и новый эксперимент различаются: в replay подаётся сохранённая decision tape; новый запуск модели даже с тем же seed не обещает те же ответы. RecordedDecisions не выдавать за latency-реалистичный live rollout. Время reasoning в облаке не влияет на игровые дедлайны; реальные latency замерять отдельно.
