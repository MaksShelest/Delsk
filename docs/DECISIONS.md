Ограничение интерфейса «одно назначение продукции» не запрещает расширение списка маршрутов в будущем.

Публикации и реклама сохраняются как продуктовое направление исходной спецификации. Никаких платежей, публикаций, подключения рекламного SDK или модели к коммерческому выпуску архитектурный этап не делает.

Сценарий должен иметь путь восстановления при нулевых деньгах: добыча → физическая лавочка → доступная стартовая продажа сырья. Покупка через заказ требует залог, поэтому **baseline городская закупка сырья из наличия** предусматривается как отдельная маленькая bootstrap-заявка/покупатель в торговой точке с оплатой при физической передаче, без обещания будущей поставки и без залога. Она использует обычный pickup/наличный settlement, учитывается в общем внешнем бюджете, не даёт бесконечные деньги бесплатно. Это необходимое техническое уточнение условия восстановления §7.1/10.3; поставочные договоры при нуле денег всё ещё нельзя заключать без залога. До реализации проверить, что бюджет/товарные веса всегда оставляют положительный спрос хотя бы на доступное стартовое сырьё.

**План выбора TFM:** первым маленьким экспериментом проверить Core+Hosting+Algorithmic и runner/test с `net10.0`, а Godot-проект — сначала штатный сгенерированный `.csproj`, затем поддерживаемый им общий target. Не менять шаблонные Android PropertyGroup вслепую. Если `net10.0` не поддерживается выбранным экспортом, общий код нацелить на минимальный совместимый TFM, подтверждённый этим экспортом (кандидат `net8.0` для библиотек при host SDK10 и Android target из шаблона). Это изменение target framework, **не переписывание ядра**; точная пара и необходимость targeting packs фиксируются отчётом эксперимента. Если нужен старый runtime, проверить его срок поддержки и не объявлять решение готовым к публичному выпуску. Если устойчивого C# Android экспорта не получается, продолжить независимое ядро, отдельно сообщить блокер; переход движка/языка — крупное решение пользователя.

Порядок проверки: версии и SDK availability → restore/build/test маленькой библиотеки → Godot headless import → запуск простой сцены с тем же core → Windows export → Android export → подписанный тестовый APK на реальном устройстве → save/load/pause/kill/relaunch. Установка APK в эмулятор полезна, но не заменяет телефон. При отсутствии телефона критерий остаётся открытым, даже если CI создал APK.

Рекламный плагин — отдельный ранний эксперимент после базового экспорта; коммерческая интеграция не относится к первому циклу. В этой итерации нет отдельной перевозки самой машины от городского магазина; ранее существовавший груз не переносится покупкой. Машина закреплена за выбранным узлом, переназначение/перемещение техники — будущее расширение. Это техническое упрощение продаж/размещения, без добавления нового транспорта.
- Upgrade оплачивает полную цену следующего уровня, без возврата старой стоимости/материалов; требует присутствия владельца, Off и отсутствия личного/автоматического цикла. Сохраняются EquipmentId, StorageId, содержимое, GroupId, фактический штат, ставка и её pending значения. Растут характеристики/места. Оплата и вместимость меняются одной транзакцией, переполнение текущей/отложенной зарплаты проверяется до commit.
- Режимы Off/Personal/Automatic. Личная команда Harvest с EquipmentId использует свой инвентарь участника, резервирует запрошенное место, занимает его на `ceil(quantity/cycleQuantity)×cycleTicks`; последняя неполная партия выдаёт ровно запрошенное количество. Весь личный результат поступает при завершении команды, как прежняя ручная добыча. Без экипажа/зарплаты/энергии. Во время этой команды нельзя перемещаться или менять режим машины; отказ EquipmentBusy сохраняет действие. Без техники прежняя Harvest остаётся доступна и при cash0.
- Автоматический цикл выдаёт полную каталожную партию в buffer оборудования. При N≥minCrew progress+=N, required=cycleTicks×crewCapacity; заработок выплачивается за фактически работающий интервал. Выходное место резервируется при старте, но сырьё ещё не считается наличием. Work/pay выполняются атомарно; недостаток денег/места/штата не создаёт товар. Топливо/ремонт и дополнительная энергия добычи не вводятся; стартовый расход — зарплата.
- Off немедленно сохраняет automatic WIP/место, прекращает работу и оплату; N уходит постепенно. Возврат Automatic продолжает тот же цикл. Personal/upgrade при WIP отклоняются — сначала завершить цикл. Если N упал ниже minCrew, начатый цикл тоже ждёт, без оплаты; не теряет progress. Это простой вариант безопасной паузы, без механики отмены партии.
- Готовность пустого automatic экипажа игнорирует только недостаток N: узел, mode, buffer и деньги на minCrew должны быть доступны. Заполненный buffer не привлекает людей; личный режим не привлекает оплачиваемый экипаж. Предприятия и машины используют один расчётный план бюджета; обработка work обеих ролей ротируется по общему каноническому списку групп, чтобы production не всегда получало деньги первым.
- LaborWorkplace — небольшая временная запись группы/minimum/readiness/расчёта стоимости для одного кадрового шага. Она не хранится в мире и не требует интерфейса/DI/framework. Сериализуемыми остаются конкретные production/extraction состояния. Общий hash включает equipment, автоматический WIP/holds, ссылку личной работы на машину и все группы. Полный load ещё P12.
- Buffer разгружается через обычный Transfer только с участником у узла; продажа требует реального пути в терминал. Машина может работать, пока владелец идёт в другое место; результат остаётся в buffer. Чужие private EquipmentView/склады не передаются контроллеру; каталог копируется, публичные N/role/wage видны в LaborMarket.
- Все прежние bounded regression прогоны сохранены численно. Форма DTO изменила hashes; platform expectations обновлены после отдельной проверки балансов. [Отчёт](IMPLEMENTATION_REPORT_P11.md), [границы доступного прототипа](PROTOTYPE_STATUS.md).

- Capital future и spot используют один CapitalOffer/remaining/hold, без новой capital-order сущности/бюджета. Одна совокупная request на actor/окно: нельзя одновременно spot и future. Это сохраняет bootstrap path без залога и общий финансовый лимит. Compensation account внутри accounting, не дополнительный political participant; refunded capital money остаются CapitalBudget без автоматического повторного заказа (P18).
- R/I в P16 равны0: personal carrier stock пока свободный и не назначен конкретному договору. Исполнение учитывается при physical receipt. P17 добавляет exclusive подготовку/погрузку/грузы/return capacity/ETA и automatic quota. Late manual delivery отклоняется и сохраняет carrier goods; автоматического возвращения пока нет.
- DTO/projections/hash/checkpoints/export ownership расширены вместе. Research delivery.json содержит buy offers, active supply requests и contracts, scenario.json — настройки. Terminal исторические contracts/accounts сохраняются с0 current escrow/bond и без capacity hold. Секретные political contracts в эти общие projections добавлять нельзя.
- World4/Rules delivery-1 явно несовместимы с World1–3, миграции нет. Session2/Envelope1 не менялись. Новые saves писать отдельным путём, прежние открывать прежним кодом. Platform canonical shape/hash меняется даже в пустом delivery; контрольные денежные/товарные числа прежних сценариев проверены до обновления expectations.
- Первые4 capital tests отказали из-за ошибки fixture: terminal был на private shop plot. Он перенесён на отдельную public cell; rules land validation сохранены. Полная повторная регрессия прошла; детали и реальные gates — отчёт P16.


## 16. Решения P17a и исследовательская готовность

Автор: Шелестов Максим Евгеньевич.

- Выполнена первая вертикальная часть P17; весь P17b/месячный объём сохранён. Один enterprise output/transport slot, существующий delivery contract, реальный full round trip. Incoming queue/свои destinations/upgrade/полный late-return gate/P21 autonomous transport goals ещё не готовые системы.
- Использованы прежние defaults: purchase20000minor, cargo volume10, move1tick/cell, minimum/capacity crew2, wage25. Покупка N0. В S6 fixture Labor step1/mobility1 ускорены явно, чтобы показать настоящий наём из population4 в коротком сценарии; обычный default step10/mobility1/10 не менялся.
- Prepare в phase4/load на следующем phase2 barrier. Planned arrival=load+max(1,path cells×moveTicksPerCell), return столь же долгий. Один scheduling tick не teleport; зарплата только за actual travel ticks после load, включая конечный return tick, из полного upper budget. Quantity берётся из contract U/source/cargo space, payload quantity не принимается.
- Полный wage hold защищён от spend другими предприятиями. Active trip labor readiness не расходует этот же бюджет повторно; payroll actual N×committed wage, unused released after return. Wage pending на end+1, attraction не раньше pay effective. Overflow wage×capacity×максимальный fixed path проверяется до принятия ставки/настроек, а не рушит future work.
- R/I теперь реальные counters, cargo stock hold подкрепляет I, source stock hold — R. Manual receipt ограничен U; generic Transfer из/в managed cargo запрещён, в том числе попытка добавить unrelated goods. Возвратное место резервируется атомарно с load после освобождения source stock; timely receipt освобождает его.
- TripRef lifecycle и financial contract lifecycle независимы: Fulfilled на outbound arrival не обнуляет return route, payroll или численность. Начатый trip не остановится от route disable. Late cargo primitive не исчезает; полный controlled late experiment остаётся P17b.
- World5/Rules logistics-1, Session2/Envelope1. World1–4 отклоняются без migration. Старые saves не удалять/не overwite; новая Godot/проверочная output path версии. Новый logistics.json входит в byte continuation; исследования читают фактические выгрузки C#.
- Первая build не прошла CS0136 (pattern variable/new local одинаковое имя), исправлено. Один ранний baseline command был запущен со старыми assemblies после failed build и исключён из evidence текущего кода; заново построенная версия и baseline249 проверены. Итоговый headless281/11 scenarios/8 load pairs реально прошёл. Эти факты отражены в отчёте, не подменяются count предыдущей сборки.
- Готовность согласованного MVP оценена приблизительно~60% (субъективные веса, не percent time/code). Полная algorithmic headless система после P21; real-model pilots P22/P23, основные series/analysis P24/P25, UI P26 не нужен вычислительному эксперименту. Подробные предложения и первичные источники — RESEARCH_READINESS.md. Тема/результаты диссертации этим документом окончательно не утверждены; реальный model experiment ещё не проведён.
