# Готовность MVP и предложение исследовательской программы

Автор: Шелестов Максим Евгеньевич. Дата: 14.10.2026. Состояние: P00–P16 + P17a; P17 целиком ещё не завершён.

Этот документ оценивает текущее состояние и предлагает темы. Он не меняет игровые правила, месячный объём или утверждённое направление. Тема диссертации/гипотезы ещё не выбраны пользователем окончательно; исследовательских результатов по реальной модели пока нет.

## Оценка процента

Ориентир: **около60% функциональности согласованного MVP**, разумный диапазон оценки55–65% (не статистический доверительный интервал). Это инженерная оценка по подсистемам; не измеренный процент кода, не доля затраченного времени и не прогноз оставшихся дней. Этапы различаются по сложности, поэтому число выполненных ID не является качественной мерой готовности.

Для прозрачности выбран субъективный весовой список (веса не новые требования):

| Подсистема | Вес MVP | Готовность подсистемы | Основание |
| --- | ---: | ---: | --- |
| Время/команды/детерминизм/сохранения/журналы | 10% | 100% | Общий Core, replay/direct checkpoint/валидаторы/CI |
| Экономика/производство/земля/контент/техника добычи | 20% | 100% | Утверждённые две цепочки и стартовое хозяйство готовы |
| Числовая занятость/зарплаты/простой | 10% | 100% | Salary cubed/caps/переходы, новые роли включены в общую численность |
| Торговля/контракты/расчёты/городской спрос | 15% | 75% | P14–P16 готовы; динамический спрос/волны P18 отсутствуют |
| Физическая автологистика | 10% | 50% | P17a рейс готов; upgrades/queues/inbound/output и полный late-return gate P17b остаются |
| Выборы/скрытые обязательные договоры | 10% | 0% | P19/P20 ещё не реализованы |
| Полноценные алгоритмические NPC | 10% | 50% | P13 развивает хозяйство; market/contracts/politics goals P21 ещё не готовы |
| Игровой Godot UI/ручная игра/устройство | 5% | 0% | Технический probe не равен игровому интерфейсу; телефонный gate открыт |
| Локальная модель/серии/статистический анализ | 10% | 0% | P22–P25 ещё не реализованы; текущий экспорт поддерживает будущие исследования |

Взвешенный ориентир61.25%, округлён до~60%. Веса можно уточнять без изменения правил; они нужны лишь объяснить оценку. Значительная часть оставшегося объёма сложна: интеллект, политические взаимодействия и корректный экспериментальный протокол.

## Когда начинать исследования

| Состояние | Что доступно | Что нельзя заявлять готовым |
| --- | --- | --- |
| Сейчас, после P17a | QA, воспроизводимые экономические/транспортные пилоты, сохранение/восстановление, локальное измерение стоимости расчёта | Полная политико-экономическая партия, эффект LLM, человеческое игровое тестирование |
| После P21 / Gate C | Полноценная headless партия без LLM: спрос, автоматика, выборы, договоры, все необходимые алгоритмические цели | Сравнение с ещё не подключённой реальной моделью |
| После P22–P23 и фактического запуска локальной модели | Пилот сравнения алгоритма/гибридного контроллера, ошибки формата/таймауты/задержки/fallback, измерение ресурсов | Fake adapter/test reply не заменяет реальный модельный эксперимент |
| После P24–P25 | Основные повторяемые серии, версии протокола/конфигураций, парные seeds, статистика/графики/таблицы | Научный результат не возникает автоматически от завершения кода: нужны реальные данные/анализ |
| После P27 / Gate D | Итоговый пакет воспроизведения/регрессии и известные аппаратные ограничения | Из этих игровых экспериментов нельзя автоматически выводить поведение реальной экономики/людей |

Godot UI P26 не является условием вычислительных экспериментов: один и тот же C# Core запускается runner без графики, с настоящими игровыми длительностями/перевозкой. UI нужен для ручной игры/тестирования людьми. Устройство проверяется отдельно, если вывод исследования касается Android performance.

## Рекомендуемая основная тема

Рабочая формулировка: **«Архитектура и экспериментальная оценка гибридных автономных NPC в воспроизводимой экономической симуляции с ограниченными ресурсами и отложенными действиями»**.

Научный вопрос: при одинаковой разрешённой информации и ограничениях насколько модельная помощь в выборе стратегии улучшает качество решений относительно utility-контроллера, и какой дополнительной задержкой/памятью/вычислением это оплачивается?

Предлагаемая гипотеза (её надо проверять): гибрид «алгоритм выполняет безопасные операции, модель редко выбирает стратегию» даёт лучший компромисс качество/стоимость, чем один алгоритм и более частое модельное управление. Гипотеза допускает отрицательный результат: более частые вызовы могут ухудшить исполнение из-за задержек/устаревшего состояния.

Контроли: текущий utility baseline; algorithmic baseline с тем же decision interval/apply delay; гибрид с ограниченным budget; вариант более частой модельной переоценки, если совместим с общими лимитами. Это настройки исследовательского сценария, не обещание изменить default gameplay. Рутинные действия у всех идут через один validator/command budget. Политические веса/цели сравниваемых сторон фиксируются, а не меняются вместе с типом контроллера.

Основные метрики: доля выполненной контрактной стоимости/объёма, производственный выпуск, денежный результат с отдельным учётом вложений, доля побед и время до победы, простои, command rejections, model format errors, stale answers, fallback rate, p50/p95 inference latency, количество запросов/tokens, пиковая RAM и время расчёта. Денежный результат/победа не заменяют друг друга и не объединяются произвольным итоговым баллом. Размеры инвестиций учитывать отдельно; расходы на технику сами по себе не означают плохое решение.

## Дополнительные темы

| Тема | Проверяемый вопрос | Сравнение | Метрики |
| --- | --- | --- | --- |
| Устойчивость к задержкам и устаревшим намерениям | При какой задержке модельная помощь теряет преимущество? | Разные decision/apply delays и таймауты при том же мире/информации; fallback variants | Срыв срока, stale/fallback/rejection rates, прибыль/победа, стоимость вычислений |
| Память и ограниченная публичная информация | Помогает ли история разрешённых торговых/экономических событий? | Короткая/длинная история, без дополнительной чужой секретной информации | Исполнение сделок, качество выбора плана, повторение неудачных действий, tokens/latency |
| Кооперация/доверие и политические обязательства | Как стиль контроллера влияет на приобретение поддержки и исход выборов? | Fixed political objectives/trust settings, algorithmic/hybrid, одинаковый ресурсный бюджет | Подписанные и исполненные компенсации, стоимость собственного блока поддержки, победы/срок, устойчивость к контрагентам |
| Устойчивость собственной экономики | Как баланс TTL/штрафа/спроса влияет на доступность развития и исполнение? | Только разрешённые balance parameters, версии JSON/одинаковые seeds | Выпуск/запасы, численность/безработица, простои/неисполнение, распределение денег |

Основная тема и задержки/память образуют компактную программно-инженерную диссертацию. Кооперацию можно оставить дополнительным экспериментом после P20/P21. Не стоит одновременно обещать исследование всех четырёх тем и человеческой правдоподобности NPC.

## Минимальный протокол (предложение для P24/P25)

1. Зафиксировать commit/rules/config hash, сценарий, горизонт/правило завершения, версии моделей/quantization/runtime, разрешённое наблюдение и цели. Заранее выбрать одну primary metric и secondary metrics; сохранить неуспехи, а не только удачные партии.
2. Провести небольшой пилот, например10 seeds. На нём проверить работоспособность/variance/стоимость и выбрать размер основной серии.30 seeds на условие — стартовый ориентир, не доказательство достаточной статистической мощности.
3. Основные условия сравнивать на парных world seeds, менять позиции/ID контроллеров сбалансированно; baseline/гибрид получают одни права/условия. Единица наблюдения — независимая партия/seed, а не каждый tick. Несколько NPC одной партии не считать независимыми повторениями.
4. Отдельно контролировать бюджет решений: native fast algorithmic baseline и budget/delay-matched baseline. Не давать алгоритму скрытую информацию и не выдавать privileged research dump модели. Секретные договоры доступны только сторонам даже в history ablation.
5. Для LLM различать качество решения и фактическую задержку. Быстрый headless может дать модели всего миллисекунды на десятки игровых тиков; тогда сравнение измеряет преимущественно fallback, а не её стратегию. Использовать явный paced протокол для живой модели либо отдельно готовить decision-counterfactual эксперименты на сохранённых observations/snapshots. Подготовка ответа вне прогона не называется live inference; replay не называется новым независимым модельным запуском. Core никогда не ждёт HTTP внутри Step.
6. Записывать наблюдение/ответ/команду/причину принятия/время, budget/queue/cancellation/epoch/model metadata. Повтор recorded decisions должен воспроизводить trajectory. Fresh LLM run может отличаться даже при одинаковом seed: сохранять реальные outputs и повторы, не обещать побитовую детерминированность inference.
7. Рассчитать paired effect sizes и доверительные интервалы по партиям; latency показывать отдельно p50/p95, win rate — вместе с количеством партий. Учесть множественные сравнения/выбранную primary hypothesis. Итог — воспроизводимый dataset + CSV/JSONL + графики/таблицы + команды повторения + границы применимости.

Размер серий/модели/аппаратное обеспечение и итоговую формулировку темы согласовать с научным руководителем на основании пилота. Этот документ не утверждает, что data collection/statistical analysis/model inference уже выполнены.

## Связанные первичные публикации

- [Economics Arena for Large Language Models](https://arxiv.org/abs/2401.01735), 2024: динамические конкурентные экономические игры, влияние доступной истории и соблюдение правил. Это основание иметь сильный baseline и явно фиксировать информацию.
- [Generative Agents: Interactive Simulacra of Human Behavior](https://arxiv.org/abs/2304.03442), 2023: архитектурные ablations наблюдения/планирования/рефлексии. Полезно как пример сравнения компонентов; человеческая правдоподобность не равна финансовой эффективности нашей игры.
- [Business Arena: Benchmarking LLM Agents in a Realistic Marketplace](https://arxiv.org/abs/2608.08621), 2026: долговременные бизнес-решения, сравнение с заданными стратегиями и анализ факторов результата. Само существование экономической арены уже не достаточная заявка на новизну. Предлагаемый вклад Delsk — измерение ограниченного гибридного управления, временных обязательств и надёжности исполнения; novelty review ещё требуется.
- [ODD Protocol: Second Update](https://www.jasss.org/23/2/7.html), 2020: ясное описание purpose/state/time/scheduling/initialization/submodels и воспроизводимости. Для диссертации подготовить описание модели в таком духе, со ссылками на версионированные правила/код; individual inhabitants добавлять ради протокола не нужно.

Список прочитанных первичных источников ограничен выбранными работами; это начало literature review, не полный обзор и не утверждение об уникальности предложенной темы.
